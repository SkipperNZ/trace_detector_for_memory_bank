# Контракт данных v1

Дополнение для текущего эксперимента: import-sentiment создает входы
input_version=sentiment-message-only-v1, metric_version=agent-dissatisfaction-message-v1,
context_scope=message_only, history_available=false. В нем context_status=complete означает
полноту самого сообщения, а не наличие истории. Судья видит это ограничение. Исходные
POSITIVE/NEGATIVE/NEUTRAL и причины сохраняются отдельно от входов.

judge экспортирует метки с label_source=llm_judge, judge_version и runtime_status=ok. Они
принимаются для обучения и сравнения с явно выбранным источником llm_judge. Обязательного
требования человеческой разметки для нынешнего пилота нет. Прежний human-контракт ниже
сохранен как опциональный режим; его label_source не следует присваивать ответам модели.

Все файлы — UTF-8 JSONL, одна запись на строку. Пути обрабатываются через `pathlib`.
Неизвестные поля сырого события отвергаются: преобразование экспорта должно быть явным.

## Событие

```json
{"tenant_id":"demo","trace_id":"session-1","event_id":"u1","parent_id":null,"branch_id":"main","sequence":0,"role":"user","visibility":"user_visible","text":"Напиши пример на Python.","language":"ru","group_id":"project-17"}
{"tenant_id":"demo","trace_id":"session-1","event_id":"a1","parent_id":"u1","branch_id":"main","sequence":1,"role":"assistant","visibility":"user_visible","text":"Вот код на Java.","language":"ru","group_id":"project-17"}
{"tenant_id":"demo","trace_id":"session-1","event_id":"u2","parent_id":"a1","branch_id":"main","sequence":2,"role":"user","visibility":"user_visible","text":"Ты проигнорировал мою просьбу про Python!","language":"ru","group_id":"project-17"}
```

| Поле | Значение |
|---|---|
| tenant_id, trace_id, event_id | Непустые строки. Тройка — идентичность события |
| parent_id | ID непосредственного предка в том же tenant/trace; null только для корня |
| branch_id | Ветка из доверенного лога; переход к общей родительской ветке допустим |
| sequence | Целое число ≥0, строго больше sequence родителя. Ветки могут иметь одинаковые номера |
| role | user / assistant / tool / system |
| visibility | user_visible / internal; определяется транспортом, не содержимым текста |
| text | Строка с фактически доставленным содержимым |
| status | completed (по умолчанию) / partial / cancelled |
| language | ru / en / mixed или иной код; по умолчанию unknown, вызывающий проверку |
| group_id | Необязательный ID независимой группы, одинаковый во всех событиях trace |

В этой версии trace соответствует сессии со всеми ее ветками. Несвязанные сессии не следует
объединять. `group_id` обозначает проект/пользователя/кластер дубликатов в пределах tenant;
если его нет, split делается по trace. Связанные шаблоны и переводы должны получить одну группу
**до** разбиения. Автоматического поиска близких дубликатов пока нет.

Повтор доставки той же записи удаляется. Конфликт одного ID с разным содержимым — ошибка.
Циклы и обратный порядок — ошибка. Отсутствующий предок сохраняется как `missing_parent`;
нельзя «починить» такой экспорт, объявив обрезанное начало настоящим корнем.
Для изменения содержания существующего события нужен новый ID/версия экспорта.

Для недовольства применимы только завершенные user_visible user-сообщения. Видимые завершенные
предки user/assistant/tool включаются в контекст; internal/system исключаются, но обход их
родительских связей продолжается. Неотправленные и отмененные сообщения исключаются.
Число trace без применимых сообщений сохраняется в манифесте.

## Подготовленный вход и версии

Вход содержит scope, target_event_id, context, context_status, версии рубрики и сериализации,
input_id, language, group_id, split. `input_id` — SHA-256 канонического JSON с tenant,
trace, branch, целью, видимым контекстом, лимитом и статусом. Он меняется при восстановлении
пропавших предков или смене входа. Каждый запуск сохраняйте в отдельный каталог, если нужно
сохранить прошлую версию; при повторном указании того же `--out` файлы заменяются атомарно.

`max_chars` ограничивает сумму длин текстов, а не токены или полный JSON. Цель сохраняется
целиком; старые видимые предки удаляются только с начала. Любое удаление помечается явно.
ML-runtime дополнительно проверяет полный сериализованный вход своим tokenizer.

## Разметка и scores

Шаблон аннотации создается автоматически. Обязательны label yes/no/unclear, annotator,
label_source=human, metric_version. Для yes evidence_event_ids включает ID целевой реплики;
все evidence принадлежат переданному causal context. Оценки учителя не принимаются за human gold.
Двойная разметка и согласование выполняются вне CLI.

Минимальная запись для импорта score другого детектора:

```json
{"input_id":"SHA256_ИЗ_PREPARE","score":0.72,"runtime_status":"ok","model_abstention":false,"model_version":"candidate-and-revision-v1"}
```

score — конечное число [0,1] либо null; направление — больше означает вероятнее недовольство.
runtime_status — ok/error/not_evaluated/missing. Ошибка, отсутствие score, неизвестный язык,
отказ модели или неполный context вызывают дополнительную проверку. score не обозначает
финальную метку. При полном падении процесса CLI завершается с ошибкой и не создает файл scores;
старый файл результатов не следует использовать как результат нового запуска.

## Решение по трейсу

`filter_selected` объединяет пороговые срабатывания и обязательную проверку при проблемах входа.
Их списки сохранены отдельно: model_selected_ids и safety_selected_ids. Аудит применим только
к неотобранным: стабильный равномерный hash от seed, tenant и trace сравнивается с audit_rate.
Seed нужно выбрать до просмотра исходов и сохранить. Это воспроизводимая псевдослучайная
реализация Bernoulli-дизайна, не криптографическая защита от управляемых ID.

`would_route` описывает каскад, `routed` — фактическую очередь выбранного режима.
В shadow inclusion_probability=1; в cascade вероятность равна 1 для фильтра и audit_rate для
остальных. Параметры и SHA политики сохраняются в каждой записи. Частота считается только
по фактическому routed и inclusion_probability. Нулевая вероятность аудита не допускается.
