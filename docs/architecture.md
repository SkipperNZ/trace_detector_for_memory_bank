# Архитектура и план исследования

## Изменение плана: LLM-разметка без людей

14 сентября пользователь уточнил: человеческая разметка сейчас недоступна. Рабочий протокол
перенесен в README: публичный agent-trace-sentiment → Qwen LLM-as-a-judge → анализ согласия/
повторяемости → обучение на псевдометках. Подключен реальный llama.cpp deployment. Старые
разделы ниже описывают первоначальный исследовательский план и необязательный будущий human gold;
они не блокируют текущую работу и не являются требованием собрать людей для разметки.

Текущая базовая версия принята пользователем 14 сентября: 100 совпадений из 120 входов
с автоматическими метками источника (83,3%), macro-F1 0,836. Она возвращает только
NEGATIVE / NEUTRAL / POSITIVE; оценка претензии к агенту сохранена лишь в старом режиме.
История агента в этом датасете отсутствует, метки учителя помечены llm_judge.
[Выполненный план студентов](experiments/sentiment-student-plan.md) определяет текущую ветку
и заменяет исторические этапы ниже, где фигурируют human gold или неподключенный API.
Человеческая разметка не требуется для обучения и сравнения студентов с учителем.

Зафиксировано 14 сентября 2026: сейчас Windows, дальнейшая работа на macOS и Linux;
основной язык пользователя — Python; на рабочем оборудовании будут более мощные NVIDIA GPU.
Из переписки: исследуем и высокую полноту обнаружения, и мониторинг частоты проблем.
Точная модель GPU, объем потока, целевой recall и допустимая цена пока неизвестны.

## Решения

Один Python-пакет с импортируемыми функциями и CLI. Базовый офлайн-пайплайн работает без
ML-зависимостей. Модули разделены по входам, маршрутизации, статистике и моделям, чтобы знакомому
с Python ML-инженеру было удобно менять эксперимент без изучения отдельного сервисного стека.
JSONL — исходный переносимый формат; Parquet и DuckDB имеют смысл при росте объема. Текущая
версия загружает экспорт в RAM и обходит предков каждой цели, то есть предназначена для пилота,
а не для неограниченного production-журнала. На длинных цепочках обход может быть квадратичным.

В трехклассовой ветке реализованы TF-IDF, замороженный E5 с логистической головой
и дообучение E5 по меткам фиксированного Qwen. По calibration выбран дообученный E5;
[результаты](experiments/sentiment-students-2026-09-14.md) получены на оставленных сессиях.
Для новых сообщений есть `make_sentiment_input`, для запуска — `predict-sentiment`.
Старый бинарный интерфейс сохранен отдельно. Общий многозадачный loss и SetFit
остаются возможными будущими экспериментами с независимой проверкой целевой рубрики.
Неразмеченные задачи никогда не превращаются автоматически в отрицательные примеры.

Мощное оборудование учитывается параметрами устройства и размера батча. Данные, схема метрик
и маршрутизация не зависят от GPU. На macOS доступен MPS при поддержке установленным PyTorch;
на Windows/Linux возможна CUDA; везде предусмотрен CPU. Такой выбор устройств поддерживает
[Sentence Transformers](https://www.sbert.net/docs/package_reference/sentence_transformer/model.html).
Установку PyTorch под драйвер и платформу определяет [официальный selector](https://pytorch.org/get-started/locally/).
Внутри пакета нет обязательных CUDA-расширений, FlashAttention, Docker или Linux-only сервера.

Для небольшой замороженной модели первым шагом на сильных картах будет увеличение batch size,
затем измерение latency/throughput. Для более дорогого обучения можно добавить CUDA-профиль,
bf16 и распределение работы. Несколько GPU пока не поддерживаются одной командой; можно вести
независимые эксперименты на отдельных устройствах через окружение процесса. Числа скорости,
VRAM и выгоды для A100/H100 не предполагаются заранее. Выбор большей модели должен улучшать
качество на той же проверке, а не следовать просто из наличия памяти.

Установка обычным pip не зависит от uv; при необходимости uv может управлять тем же
[pyproject и optional dependencies](https://docs.astral.sh/uv/concepts/projects/dependencies/).
Для каждой реальной серии экспериментов нужно сохранять окружение/lock под выбранный runtime.
Сейчас переносимы исходники и формат головы; побитовая идентичность CPU/MPS/CUDA не обещается.
В артефакте головы записаны версии основных библиотек, Python, устройство, checkpoint SHA,
группы обучения и хеш входов. Полного транзитивного ML-lockfile пока нет.

## Эксперимент A: полнота обнаружения

1. Восстановить доверенные события и разметить первые 200–300 разнообразных сообщений
   двумя русскоязычными аннотаторами. Это объем разведки из исходного исследования, не гарантия recall.
2. Согласовать рубрику: явная претензия к агенту отличается от спокойной коррекции, внешней жалобы,
   цитаты, новой задачи и неясного адресата. Отдельно сохранить частоту unclear.
3. Разбить независимые группы; старые просмотренные данные оставить в development pool.
   Сформировать свежий человеческий test отдельно от подбора модели и threshold.
4. Сравнить no-filter, общий энкодер с головой; при необходимости импортировать scores NLI/GLi
   через тот же контракт. Эти модели не встроены и автоматически не скачиваются.
5. На calibration сравнить заранее заданные пороги, полные routed traces/messages и нижнюю
   границу trace recall. Сохранить режим обработки ошибок. Заморозить единственную политику.
6. Проверить ее на свежем test и отдельно измерить качество размещенного судьи на тех же
   причинных входах. Только после этого обсуждать жесткий отсев и production.

Пакет считает filter trace recall, model message recall и filter message coverage отдельно.
Аудит входит только в показатели маршрутизации с аудитом. Shadow-направление всех трейсов
не выдается за полноту модели. Нижняя односторонняя 95% граница использует точный биномиальный
метод и применима к независимым репрезентативным положительным трейсам при замороженной политике.
Если в данных есть несколько traces одной group_id, биномиальная граница отключается;
нужен отдельный кластерный расчет. RU/EN/mixed-разрезы и согласие аннотаторов пока рассчитываются
вне CLI; общее значение качества не заменяет их.

## Эксперимент B: частота проблем

Нужен отдельный вероятностный контроль. Нельзя оценивать распространенность простым средним
по обогащенной выборке срабатываний. Текущий route поддерживает Bernoulli-аудит неотобранных
целых трейсов с ненулевой вероятностью. Все применимые сообщения выбранного trace размечаются;
prevalence считает HT totals yes/no/unclear и отношение yes/(yes+no). Ошибки или отсутствующие
метки не могут молча уменьшить знаменатель.

В пилоте без scores shadow/no-filter дает полный контроль. Команда `sample` создает отдельную
вероятностную выборку без ML: это cascade с детерминированным контрольным score=0 и заданным
audit_rate. Неполные входы и unknown-language проверяются с вероятностью 1, что корректно
отражается в весах. Контроль явно именуется sampling-control-v1; он не является моделью.

Взвешенные доверительные интервалы, стратификация и человеческая поправка ошибок судьи —
следующие шаги. Без human audit метки GLM оценивают частоту ответов GLM, а не человеческую истину.
Нельзя использовать исчезновение меток no/yes в пустой выборке как оценку нулевой частоты:
в таких случаях CLI возвращает null.

## Подключение реального судьи и других метрик

После появления endpoint потребуется адаптер с явным deployment manifest: модель, SHA,
шаблон, квантование, serving/runtime, параметры генерации и hardware. Очередь принимает
тот же causal input, выполняет ограниченные retries, валидирует label/evidence и записывает
фактические tokens, latency и ошибки. Содержание трейса остается недоверенными данными;
судья получает рубрику отдельно и не получает инструменты. Текущий пакет сетевые запросы судье
не выполняет, судейскую полноту и денежную экономию возвращает как null.

Циклы требуют последовательности tool calls/results, сигнатур аргументов, статусов ошибок и
признаков прогресса. Считать нужно эпизоды, а не каждое окно. Backtracking требует связей patch/
revert и определения eligible-шагов. Leaked thinking требует достоверной информации о фактически
доставленных каналах. В v1 нет таких детекторов: текстового контракта недовольства для них
недостаточно. Следующее расширение схемы должно добавить эти поля с явной версией.

Для production потребуются инкрементальный обработчик, персистентная очередь, хранилище
версий, редактирование чувствительных данных, изолированный tenant-cache, мониторинг дрейфа
и профилирование полного конвейера. На текущем объеме их разработка до первых данных
увеличила бы стоимость проверки основной гипотезы. Предусмотренные версии и стабильные
идентификаторы позволят добавить их без смены смысла разметки.

Обнаружение недовольства не устанавливает причинное влияние Memory Bank. Для этого отдельно
нужен MB-on/MB-off эксперимент с изоляцией памяти по пользователям/проектам, одинаковыми
моделями и бюджетами, объективной успешностью задач и слепой оценкой.
