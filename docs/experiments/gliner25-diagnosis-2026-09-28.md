# Почему GLiNER2.5-Decide слабо совпадает с нашей разметкой

Диагностика от 28 сентября 2026. Тот же checkpoint
`fastino/GLiNER2.5-Decide@5a7adf72a23b4d311abae6ce050d7f0012bb3416`, без обучения весов.
Все новые варианты проверены **только на calibration**: 1 157 входов, 1 154 с метками Qwen.
Исходный [test-бенчмарк](gliner25-decide-2026-09-28.md) не изменён.

## Что удалось установить

Модель работоспособна на типовых задачах классификации. На нашей задаче одновременно
проявляются чувствительность к описанию классов и слабый перенос на специальную рубрику
обратной связи об агенте. Простое изменение формулировок не устранило проблему.
Бинарное недовольство оказалось существенно перспективнее исходной трёхклассовой постановки.

### Контроль на публичных development-данных Fastino

| Раздел | Совпадение с метками источника |
|---|---:|
| Тональность отзыва | 84 / 100 |
| Передача обращения человеку | 76 / 100 |
| Тип документа | 79 / 100 |

Ревизия датасета `fastino/fast-decisions`: `1a33070cabf94ce2e29105482dd2ef6c157ad7f2`.
Тексты и наборы меток переданы модели, `true_label` используется только после инференса.
Веса, библиотека и устройство те же, что для наших ablation-прогонов. Это проверка на
трёх публичных development-разделах, **не воспроизведение рекламных 60,2%**: рекламный
результат относится к другому, закрытому test из 17 разделов.

### Форма нашей трёхклассовой задачи существенно меняет предсказания

Везде одинаковые входы и исходные классы, без изменения меток Qwen. Варианты заданы
до получения их результатов; диагностика исследовательская, отдельного holdout для неё нет.

| Вариант | Mean macro-F1 | Недовольство: precision / recall yes | Исправление: precision / recall yes |
|---|---:|---:|---:|
| Исходная compact-схема | 0,3921 | 52,4% / 18,0% | 43,8% / 12,7% |
| По одной задаче за вызов | 0,3208 | 0,0% / 0,0% | 26,1% / 36,4% |
| Смысловые названия вместо no/yes/unclear, описания сохранены | 0,4020 | 36,5% / 50,8% | 36,7% / 20,0% |
| Убраны описания классов, вопрос сохранён | 0,3991 | 32,3% / 65,6% | 14,3% / 34,5% |
| Смысловые названия без описаний, вопрос сохранён | 0,4063 | 31,0% / 65,6% | 24,0% / 16,4% |

Удаление описаний помогает находить больше жалоб, но увеличивает ложные срабатывания.
У исправлений precision падает особенно сильно. Лучший общий macro-F1 вырос лишь с
0,3921 до 0,4063. Одновременное решение двух задач не оказалось основной причиной:
разделение вызовов ухудшило общий результат.

До этой диагностики длинная rubric-схема уже дала 0,2906 против 0,3921 у compact на
той же calibration. Для этого checkpoint больше пояснений не означает выше качество.

### Удаление unclear — отдельный, более простой эксперимент

Убрали `unclear` из схемы и заново выполнили инференс. Для оценки исключили сообщения,
которые Qwen пометил `unclear`; они не превращаются в `no`. Поэтому эти числа нельзя
сравнивать напрямую с основным трёхклассовым macro-F1.

| Признак | Однозначных меток | Precision yes | Recall yes | F1 yes |
|---|---:|---:|---:|---:|
| Недовольство | 1 140 | 58,3% | 57,4% (35 / 61) | 0,579 |
| Исправление | 1 094 | 33,6% | 33,6% (37 / 110) | 0,336 |

Это не просто перераспределение вероятностей после softmax. Если оставить исходные
трёхклассовые logits и только запретить выбор `unclear` при декодировании, recall на
тех же однозначных метках составляет 24,6% / 13,6%. Изменение самой входной схемы
меняет представление текста и оценки остальных классов.

Следовательно, `unclear` здесь не работает как надёжный механизм отказа при неуверенности.
Это обычная семантическая метка, которой модель должна научиться придавать наш смысл.
Отдельное решение о передаче на проверку следует калибровать, а не отождествлять с ней.

## Разбор примеров и исключённых причин

На синтетической однозначной фразе «Your answer is useless and I am disappointed in
your work.» исходная схема выбирает `no` для недовольства. После удаления описаний —
`yes`, как и в бинарной схеме. На «You forgot to add the tests I requested.» исходная
схема выбирает `no` для исправления, бинарная — `yes`. Эти примеры созданы для диагностики,
не взяты из test и не являются отдельным репрезентативным benchmark.

- **Длина:** все 61 положительных примера недовольства и 109 из 110 исправлений на
  calibration помещаются в одно окно исходной схемы. Усреднение длинных сообщений
  не объясняет основной провал полноты.
- **Язык:** в calibration нет кириллицы. Английская специализация модели важна для
  будущих русских трейсов, но не объясняет эти английские ошибки.
- **Интеграция:** исходный calibration macro-F1 воспроизведён; предыдущая проверка
  дала 80 совпадений с native API и совпадение CPU/GPU на 100 сообщениях. Загрузка
  библиотеки использует строгий `load_state_dict`, без молчаливо пропущенных параметров.
- **Уверенность:** средний максимум softmax исходной схемы — 0,423 для недовольства
  и 0,391 для исправлений. Оценки классов слабо разделены; это диагностический признак,
  а не проверенная калибровка вероятностей.
- **История и учитель:** часть реальных реплик двусмысленна без предыдущего ответа.
  Но ошибки есть и на самодостаточных синтетических жалобах. Человеческого эталона нет;
  долю ошибок Qwen и долю ошибок GLiNER данным экспериментом разделить нельзя.
- **Дисбаланс:** он делает ложные срабатывания дорогими по precision. Но GLiNER здесь
  вообще не обучался на несбалансированном train; объяснение «он выучил всегда no»
  к этому прогону неприменимо. Более сложные причины его априорных предпочтений
  требуют знания обучающих данных checkpoint, которое у нас отсутствует.

## Для чего предназначена модель и что это значит для нас

Семейство GLiNER выросло из извлечения информации, но **Decide предназначен именно для
классификации и структурированных решений**. Задача выбрана уместно. Это DeBERTa-энкодер,
который совместно обрабатывает текст и схему и оценивает допустимые ответы за один проход.
Он не выполняет генеративное рассуждение Qwen. Поддержка описаний в API не гарантирует
точного следования произвольной длинной рубрике.

Наша рубрика требует отличать отрицательную эмоцию от недовольства именно агентом,
новую просьбу от исправления его предыдущей работы, а спокойное исправление — от жалобы.
Это более специальное решение, чем обычная тональность или тип документа. Наблюдения
согласуются с недостаточным переносом на эту рубрику; точную причинную долю обучения,
формата схемы и шума учителя мы не установили.

Для дальнейшего сравнения разумны: бинарный детектор жалоб с отдельным калиброванным
отбором сомнительных случаев; дообучение GLiNER на том же train, что E5/BGE; новая проверка
на отложенных корпоративных трейсах с реальным предыдущим ответом. Ни один из этих
следующих этапов не следует считать уже выполненным или гарантией улучшения.

- [Независимый первичный разбор чувствительности к формату](https://huggingface.co/blog/Hanno-Labs/less-is-more-gliner25-decide-and-the-shape-of-a-de): другой checkpoint revision и другие задачи; его результаты не подставляются вместо наших.

Скрипт: `scripts/diagnose_gliner_feedback.py --device cpu` (или `cuda` при свободной GPU).
Нужны окружение и артефакты [основного бенчмарка](../gliner25-benchmark-guide.md), а также
три указанных публичных JSONL из закреплённой ревизии Fast Decisions в
`runs/gliner25-diagnosis-v1/`. Скрипт фиксирует варианты до инференса, сохраняет результаты
каждого варианта и не читает test. Служебные результаты остаются в `runs/`;
рядом с этим отчётом опубликованы только агрегаты и синтетические диагностические фразы.
